2.3 Retargeting：一个求解器、两条路线、六个实现

目录 hand_control/services/level_1_retargeting/。出货路径是 vector（--retarget vector 默认），angle 是诚实的对照组。

实现思路状态
L20VectorRetargetervector 求解器 + L20 配置（palm 原点、掌宽 scale、中点 seed）出货路径
L20AngleRetargeterlandmark 向量数学直出 16 角，无优化无 MuJoCo，~20–90 µs对照组
MujocoVectorRetargeter通用求解器（HTS SDK 移植，Gauss–Newton + LM 阻尼 + posture 项）底座
OrcaVectorRetargeter同一求解器指向 ORCA v1（17 关节无耦合，wrist 归手臂）已实现
IdentityRetargeter直读人手关节角，I5"逐位相同"测试的唯一参照物夹具
DexRetargeterdex-retargeting 包装stub调用即 raise；依赖决策仍开放

vector 的核心思想：匹配"两点之间的向量"而非任一点的绝对位置——robot(b−a) ≈ scale·human(b−a)。绝对匹配要求两只手共享原点和尺寸；向量匹配只要求共享形状，而形状正是遥操作真正想传递的东西。相对上游的四处刻意偏离（每一处都对应一类静默错误）：耦合矩阵 J·C（L20 有 5 个 equality 耦合关节，切列会让求解器"收敛到错的位姿"）；无状态 step()（热启动挂 self 违反 I5）；tol=0 永不早停（求解时间不许依赖数据）；在 palm site 坐标系里匹配（朝向无关，上游只有 home 朝向恰好对时才成立）。

关键实测对比（30 s 同一脚本刺激，--compare）：

优缺点一句话：vector 准（pinch 3.3 mm vs angle 22 mm）但硬（撞限位、jerk 高、每帧 ~1 ms 求解）；angle 快而柔顺、永不撞限位，但拇指是死穴——L20 拇指是 3-DoF CMC、轴经两个非轴对齐四元数串联，任何逐轴启发式都恢复不了对掌（对掌构型 (0.88, 0.66, 0.31, 0.45) 不可能被独立映射碰巧命中），tripod 误差 84 mm。所以 angle 永远是 baseline/control condition，不是出货路径。ORCA 侧：同求解器 overall 14.2 mm，需要一个 L20 不需要的旋钮 auto_scale_correction=0.72（否则拇指被要求超出 62° 外展范围）。

2.4 ★ 小拇指侧摆问题（当前最优先的 retarget 缺陷）

注意：这个问题在仓库文档里没有既有记载（文档记载的小指问题是 curl，见 §3.4）。以下机制分析是从代码推导的，四个环节各自贡献多少待实测确认。

现象：操作者小指左右侧摆（abduction），头显里的机器人小指基本不动。四个叠加环节：

  1. 机构先饱和（天花板，对所有 retargeter 成立）：人手 splay ±21°，L20 pinky_mcp_roll 限位 ±0.23 rad = ±13°——"机器人先于操作者饱和，这是机构属性不是标定错误"（l20.py 原话）。
  2. little_scale=1.35 把天花板又推高 35%：它乘的是整条向量，包括横向分量。人小指全外展横向 ≈26 mm，×1.35×全局 scale ≈ 要求 32 mm；机器人 ±13° 最多给 ±23 mm——操作者还没摆到自己的极限，pinky_mcp_roll 已经压死在限位上，之后输出恒定。这正是 vector "平均 3.7 个关节在限位"的主要来源。
  3. 权重倒挂：小指尖位置由 thumb→pinky（w=1.5）主导而非 palm→pinky（w=0.8）——小指的横向落点主要在回答"离拇指多远"，操作者相对掌面的侧摆意图是目标函数里权重更低的那项。
  4. 小增益方向被正则压制：mcp_roll 指尖增益仅 ~0.099 m/rad（该指最小），在 LM 阻尼 + posture 项下拿到最大的相对阻尼份额，加上 max_iters=8 + 热启动，每帧只挪一点。

验证判据：跑一段只做小指开合的 session，看 q[pinky_mcp_roll] 时间序列与 n_at_limit——长时间钉在 ±0.23 则环节 1+2 确认；中段来回但幅度远小于 ±0.23 则环节 4 主导。归一化不是元凶（掌宽 scale 姿态无关，有测试钉住）；真正的放大器是 little_scale 作用于整条向量。可能的修法方向：little_scale 只作用于纵向分量（沿指方向分解后再缩放）、把 palm→pinky 权重抬回主导、或给 roll 单独的增益补偿——三者都要先过 pinch 回归表再上 rig。

3 · 踩坑史（现象 → 根因 → 解法）

每一条都值一次 session。前四条是大案，后面的收进速查表。

3.1 ~90° 扭转（最贵的一次）

现象absolute 模式下虚拟手跟着走但整体扭 ~90°，且持续整场（_alignedThisRun 意味着永远）。

排查：所有嫌疑逐一测清白——设备契约 q_if_flat 8.3°、tracker→command 0.15°、anchor replay 0.2°、烘焙 mesh 与新导出差 <3°。离线重放证明命令链精确，但被命令的掌在 MuJoCo 里就偏了 94°——扭转是真的，不在画面里。

根因：连续 logcat 抓到现行——世界放置 anchor 在机器人还在 engage snap 途中 70° 时就发货了。weld_settled 比较的是被 wrist clamp 过的 mocap target，而 clamp 每周期只把 target 发到距 base 一小步、weld 同周期内闭合这一步，所以 target-vs-achieved 全程读 ~0，"settled"在 snap 中途就为真，头显把世界锁在一个扭着的机器人上。

解法：anchor 改门控在 command_reached（achieved palm 对未 clamp 的命令）+ 操作者手静止（25°/s）；头显重试对齐直到 non-yaw 残差 ≤3°。钉住它的测试：test_command_reached_sees_through_the_wrist_clamp。验证：palm-pair 9 mm 0.0°、wrist→base 172 mm 恰为设计偏置。

教训："settled" 的判据必须看穿所有会替它说好话的中间层。clamp 的存在意义就是让 target 永远离 achieved 很近——拿它做收敛判据是循环论证。

3.2 hold-flat 误触发：无人持有的完美的手

现象桌子建在离谱的高度（掌心读数 1.82 m）。

根因：HTS 在手出视野/头显被摘下时重发最后一批好 landmark——伸直、共面、完全静止，"理想的平直静止手，由无人持有"。另外竖直的手刀在几何上也"平"。

解法：四道门（tracked 必须由 source 传入不能推断 / extension / 共面性 / 掌面水平），prompt 点名失败的门（"amber 灯什么都没教，'level your palm' 才教"）。第二刀：静止阈值从 0.06 m/s 放宽到 0.10——原值是在给生理性震颤（~1 mm @8–12 Hz，70 Hz 采样下几十 mm/s 瞬时）设门，不是给意图设门；再加 0.35 s grace 吞掉真实存在的 ~0.3 s tracker glitch。

3.3 clutch 手势之死

现象操作者原话："我一捏它就卡住。"

根因：数据一锤定音——14/14 次 clutch 全部发生在抓取中，累计冻结 14.7 s。absolute 1:1 映射下没有东西需要 re-center，而任何抓握都闭合 thumb–little 距离：手势和它服务的场景已互斥。

解法：退役（保留姿态门控的能力开关，无 CLI）。教训：一个交互机制的前提被架构演进抽掉之后，它不会安静消失，会变成 bug。

3.4 小拇指 curl：1.44 个掌宽的手指

现象平手时小指末节明显弯曲（pinky_pip 63.6°）。

根因：比例不匹配且全局 scale 无法表达——L20 小指与其他三指等长（1.44 掌宽），人的小指短得多（1.17 掌宽）。求解器要匹配一个比例上偏短的目标，唯一手段是卷起来。

解法：little_scale=1.35（straight pip 63°→23°）+ little_pinch_weight 2.5→1.5（否则放大的 thumb→little 向量拖走拇指、thumb–index 闭合变差）。1.45 更直但 pinch 超 5 mm，停在 1.35。测试：test_a_flat_hand_does_not_curl_the_little_finger；参考位姿重生成并钉住。但这个修正是 §2.4 侧摆问题的放大器之一——按下葫芦浮起瓢的完整案例。

3.5 坐标基混用：不存在的 94°

现象/根因：四个基变换矩阵分在两个文件里，一个文件的向量配另一个文件的矩阵，测出 94° 的不存在误差。解法：全部收进 common_tool/.../math/frames.py，两个手写、两个是表达式（互为转置/乘积），不可能各自漂移。两条便宜的检查：行列式（异手性必须 det −1；该 −1 却 +1 = 根本没转换，手会镜像到达，而镜像的手看起来几乎是对的）；旋转按 B·R·Bᵀ 相似变换（写成 B·R 得到的矩阵仍正交仍单位行列式，动起来之前零症状）。

4 · V2（进行中）：Quest 本地跑官方 MuJoCo Unity 插件

进行中 · 调研完成流程更新：物理从 Mac 移进头显，Mac 变成控制器与记录器

相对 V1 改变了什么：物理权威从 Mac 的 Python 进程移进 Quest 上的 Unity 进程（官方插件 in-process mj_step）；渲染零延迟拿到本地物理的最新状态，烘焙网格过期问题（问题表 #5/#6）从根上消失——头显画的就是它自己算的。Mac 保留 retargeting/标定/计分栈，角色反转为控制器。

4.1 调研结论（好消息）

  • Android 编译障碍已被上游清除：最大的坑 qsort_r（bionic libc 没有）在 MuJoCo ≥3.3.0 已被自研排序替换，可无补丁交叉编译；社区有现成 arm64 预编译包（joanllobera/mujoco-bin，3.3.0/3.5.0），往 Packages/manifest.json 加两条 entry 即用。
  • 与 Meta XR SDK 共存无冲突：插件只是组件 + P/Invoke，不占相机不占 XR loader；MuJoCo body transform 每帧回写，现有 BodyVisual_* 挂到对应 MjBody 下即可，双目由 OVRCameraRig 照常出。
  • 版本三方对齐是硬约束：Python mujoco / 插件 C#（checkout 同版本 tag）/ libmujoco.so 全钉同一版本（3.3.0 或 3.5.0），否则"与训练一致"作废。

4.2 生死点与对策

一票否决项：XR2 Gen 2 跑不跑得满 500 Hz。官方插件在主线程 FixedUpdate 步进——fixedDeltaTime=0.002 意味着 90 Hz 渲染下每帧主线程塞 ~5.6 次 mj_step，与渲染和 OVR 输入抢 11.1 ms 帧预算；物理跑不满时 Unity 追帧进入死亡螺旋。第一步（1 天）：20 行 benchmark app 加载导出的 session XML 空转 mj_step 一万次，logcat 读 ns/step；单步 >1.5 ms 即判负转 V3。降到 250 Hz 能救性能但打破与训练一致——牺牲这条路的核心卖点。

若 benchmark 通过，建议一开始就做子线程物理（改 MjScene：专职线程自计时跑 mj_step 循环，主线程每帧从双缓冲抓 qpos/xpos 快照，ctrl 写入走无锁队列，约 2–4 天）——不指望 FixedUpdate。参考工程：Balint-H/modular-agents（就是在 Quest 2 上跑通的那个项目，但它也是主线程步进）。

4.3 数据链路设计

8000 上行不变：手部追踪 Quest→Mac，retarget/标定/clamp 栈完全复用
8003 新增下行：Mac 算出的 ctrl[] + mocap 目标 → Quest（adb reverse 同构，+1–3 ms USB 往返）
8002 改义：世界位姿本地就有 → 改为 Quest→Mac telemetry（qpos/qvel/contact/任务事件）
记录：telemetry 回传 Mac 落盘（现有工具链零改动）+ Quest 本地双写兜底，会话末 adb pull
场景导入：MjSpec 运行时拼装 → mj_saveLastXML 导出自包含 XML → MjImporterWithAssets

工作量估计 4–7 人周：编译+benchmark 0.5 周 · Unity 工程+场景导入 1–2 周 · 子线程步进 0.5–1 周 · 8003 协议+双写 1 周 · 标定流程适配+联调 1–1.5 周。次级风险：dexjoco 钳子等 vendor 物理要逐一验证（插件不支持 elasticity 等 engine plugin）；respawn 等运行时结构变化要改成 qpos 重置（增删组件触发整场景重建）；调试受 12 分钟 APK 循环拖累（对策：物理逻辑先在 Mac 的 Unity Editor 用桌面 dylib 验证）。

5 · V3（进行中）：4090 Linux 物理+渲染，ALVR 串流

进行中 · 调研完成流程更新：整个 Python 栈搬 4090，Unity 变 SteamVR 薄渲染客户端，头显退化为显示器+追踪器

调研中的关键转向——按变体 B′ 实施：不把物理搬进 Unity（正统做法会让会话逻辑进 C#、场景定义出现第二份），而是现有 hand_control Python 栈整体搬到 4090，Unity 只做 SteamVR 薄渲染客户端，8000/8002 协议原样走 localhost。对代码侵入近零、与训练一致性最好（与 RL/warp 同机），还顺手解决了烘焙过期问题——渲染进程可以直接读本机物理的实时状态。

5.1 调研结论

  • ALVR Linux 服务端受支持（v20.14.1，2026-07）：要求 NVIDIA 驱动 ≥535 + CUDA ≥12.1，NVENC 编码；建议 X11 会话独占 4090（Wayland 有 GPU 探测坑）。
  • USB 有线串流已官方化（v20.12+ 内置 wired mode，插线自动拉起 client）——保住 V1 用 USB 换稳定性的哲学。
  • 手部追踪不需要伴随 app：ALVR 把 Quest 手部追踪以 SteamVR skeletal input + OpenXR XR_EXT_hand_tracking 转发到 host——26 关节原始数据，不是 controller 模拟。写 ~200 行 reader 把关节按现有 8000 协议发 localhost:8000，l20_sources.py 以下零改动。
  • 固有税：延迟。ALVR 端到端 motion-to-photon 典型 50–90 ms，比 V1 本地渲染明显变差，对精细遥操作的手感是实打实的损伤。
一票否决项：Linux SteamVR + Unity XR 出双目画面的 spike（2 天）。Unity OpenXR 对 Linux 桌面 runtime 长期边缘化，SteamVR skeletal input 在 Linux 也有历史 bug——空场景出画面 + 拿到 26 关节，这两样任一不通即撤退。退路：4090 双系统 Windows host（ALVR/SteamVR 最成熟，+1 周但确定性大增）。

工作量估计 2–4 人周：spike 0.5 周 · ALVR+SteamVR 环境 0.5 周 · Unity 薄渲染客户端 1 周 · hand-tracking 桥+联调 1 周。数据记录照旧落 hand_control/data/（在 4090 上），rsync 回 Mac。次级风险：4090 box 46 GB RAM 与训练任务抢占。
