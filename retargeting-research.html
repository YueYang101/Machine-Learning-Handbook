Retargeting 的局限与候选解法
小指为什么伸不直也摆不开 · AnyTeleop / dex-retargeting 能不能治 · 六个待验证方案

这一页只做两件事：把 L20 retargeting 目前已知但未修的缺陷收敛成一个统一的根因描述，然后把可能的修法排成一张可证伪的候选清单——每一条都写清它针对哪个根因、代价是什么、用什么判据判它成功。AnyTeleop 是清单里的一条，不是这一页的主题。

前置阅读：Hand Control 技术路线手册 的 §2.3 六个 retargeter 实现与 vector/angle 实测对比、§2.4 小拇指侧摆、§3.4 小拇指 curl。那一页记录的是现象与代码机制；这一页从那里接着往前走，讲怎么修，两页不重复推导。

三十秒版本。小指的两个毛病——平手时伸不直（curl）、侧摆在头显里看不见（splay）——不是两个 bug，是同一个目标函数写法的两种表现：目标里只有指尖向量、缩放只有一个全局标量、而 L20 的小指按比例比人的长得多且不能反向伸展。
AnyTeleop（RSS 2023）用的是和我们同一条公式，而且它的缩放因子是单标量——所以它自己也有这个毛病，整包引进解决不了小指。它真正值钱的是两个可以单独抄过来的做法：Shadow Hand 配置里的中间关节向量（结构性地修 curl），以及 DexPilot 的捏合距离门控投影（修的是另一个问题——精密抓取，且有副作用）。

§ 1一个根因，两个症状

1.1 我们在解的到底是什么

出货路径 L20VectorRetargeter 每帧解这个问题（level_1_retargeting/vector.py + l20.py）：

$$\min_{q}\ \sum_{i=1}^{9} w_i \left\| R_{\text{palm}}\big(p_{b_i}(q)-p_{a_i}(q)\big) \;-\; s\cdot s_i\, v_i^{\text{human}} \right\|^2 \;+\; \lambda\left\|q-q_{\text{prev}}\right\|^2$$
$q$ 是 16 个主动关节；$p_{a},p_{b}$ 是机器人侧两个 site 的位置，经耦合矩阵 $J_{21}\!\cdot\! C$ 求导；$v_i^{\text{human}}$ 是人手对应两点的向量；$R_{\text{palm}}$ 把两边都放进各自的掌坐标系，使匹配与手的朝向无关；$s$ 是全局尺度，$s_i$ 是逐任务尺度，$\lambda$ 拉向上一帧。Gauss–Newton + LM 阻尼，固定 8 次迭代（tol=0，求解时间不许依赖数据）。

九条任务向量是：5 条 palm→指尖（权重 1.0，无名指/小指 0.8）+ 4 条 thumb→指尖 捏合向量（权重 4.0，无名指 2.5、小指 1.5）。

1.2 三个叠加的根因

根因具体是什么可核对的出处
A 目标只有指尖九条任务向量的头全是指尖（*_tip），没有任何 PIP/DIP 的约束。总长度误差要靠哪个关节吸收，完全由求解器自己挑l20.py::l20_tasks
B 单一全局缩放$s$ 是一个数，从掌宽量出来。掌宽比例对食指/中指对，对小指不对L20Kinematics.scale_for
C 机构比例L20 小指与其余三指等长，102 mm = 1.44 掌宽；人手实测 72 mm / 62 mm = 1.17 掌宽。pinky_mcp_pitch 范围 [0, 1.22] rad——不能反向伸展；pinky_mcp_roll 仅 ±0.23 rad = ±13°，人 ±21°MJCF linkerhand_l20_right.xml

A + B + C 合起来的必然结果：一条按比例偏短的目标向量，落在一根偏长的手指上，而 MCP 已经顶在 0° 停止位——唯一还能缩短「掌心到指尖」距离的自由度，就是把 PIP 卷起来。session 20260816_191302 的平手帧上，命令是 pinky_pip = 63.6°、pinky_mcp_pitch 钉在 0°、耦合的 pinky_dip 跟到 57°——就是肉眼看到的那截弯指。

1.3 现在的缓解措施，和它的代价

l20_tasks 里的两个常数（little_scale=1.35、little_pinch_weight=1.5）是针对根因 B 的局部补丁：把小指那两条目标向量单独放大，让操作者的小指「要求」的长度接近机器人小指「能给」的长度。little_pinch_weight 从 2.5 降到 1.5 是因为被放大的 thumb→pinky 会把拇指拽走，牺牲拇指–食指闭合。

不放大（baseline）63°80.7°3.2 mm

读法：补丁把 63° 压到 23°，但没有归零，而且再往上加就开始拿捏合精度换直度。原因是它没碰根因 A——只要屈曲的分配无人约束，缩放就只能在「整体够不够长」这一个维度上讨价还价。

不是元凶的两件事，写下来免得再查一遍。
（一）归一化不是元凶。全局尺度取自掌宽，MCP 排的位置在手指蜷曲时不动，所以握拳量出的 $s$ 和平手量出的一致，有测试钉住。
（二）上游那个「按平均向量长度自动定标」的机制在 L20 上是关掉的（L20VectorRetargeter.__init__ 传 auto_scale=False）。理由写在代码注释里：L20 的 qpos=0 是一只完全张开、拇指外伸 144 mm 的手，在捏合帧上按平均长度定标会得到 2.48，求解器会把八个关节推进限位。因此 little_scale 不会通过自动定标反过来影响其它手指的全局尺度——两者互不相干。--scale 的作用是让两个 session 可比（钉死后进 config hash），不是为了规避耦合。

1.4 第二个症状：侧摆

机制分析在 手册 §2.4，这里只记与本页清单相关的部分：四个叠加环节里，环节 2 正是上面那个补丁——little_scale 乘的是整条向量，包含横向分量，于是把本来就只有 ±13° 的侧摆天花板又推高 35%，操作者还没摆到自己极限，pinky_mcp_roll 已经压死在限位。手册推断这也是 --compare 里 vector「平均 3.7 个关节在限位」的主要来源——同样标为待实测确认，四个环节各自贡献多少还没有量过。两页的分工：手册那节讲四个环节各是什么，本页讲候选修法与判据。

§ 3AnyTeleop / dex-retargeting 详档

AnyTeleop: A General Vision-Based Dexterous Robot Arm-Hand Teleoperation System（Qin et al., RSS 2023），开源实现 dexsuite/dex-retargeting（本页依据 commit 3f56141b / v0.5.0，MIT 许可）。

先说清分工：AnyTeleop 的 retargeting 模块只管手指，手腕与手臂交给 CuRobo 单独规划——论文原话 “this module only considers the robot hand”。所以它和我们的对照只发生在手指这一层，我们的腕部对齐链路不在比较范围内。

3.1 它和我们是同一条公式

$$\min_{q_t}\ \sum_{i=0}^{N}\big\|\,\alpha\, v_t^i - f_i(q_t)\,\big\|^2 \;+\; \beta\,\|q_t-q_{t-1}\|^2 \qquad \text{s.t.}\quad q_l \le q_t \le q_u$$
$v_t^i$ 是人手关键点向量，$f_i$ 是机器人侧对应向量的正运动学，$\alpha$ 是「补偿两只手尺寸差异」的缩放因子，$\beta$ 是拉向上一帧的时间正则。把它和 §1.1 那条并排看：逐项对应——向量匹配、全局缩放、时间正则、关节限位为盒约束。我们多出来的是 $w_i$（逐任务权重）与 $s_i$（逐任务缩放），以及为 L20 的 equality 耦合准备的 $J\!\cdot\!C$。

换句话说，L20VectorRetargeter 实质上已经是 AnyTeleop 的 vector 模式，且在两个地方比它多一个自由度。论文与实现之间有若干差异（实现用 Huber 而非平方 L2、$\delta=0.02$ m），但形式是同一族。

3.2 $\alpha$ 是单标量——所以它自己也有小指问题

RetargetingConfig.scaling_factor 是一个 float，schema 里没有逐指 / 逐向量的字段（position 模式甚至完全没有缩放这个概念）。仓库内的取值：Allegro 1.6、LEAP 1.6、Panda 夹爪 1.5、Shadow 1.2、Schunk SVH 1.2、Inspire 1.15、Ability 1.0——都是照着食指/中指的比例定的。

把 §1.2 的推理套上去：设人手某指伸直时腕→尖距离 $L_h$、机器人该指伸直时可达最大 $L_r^{\max}$，目标向量的模长是 $\alpha L_h$。若 $L_r^{\max} > \alpha L_h$，机器人「够不着这么短的目标」，唯一手段是弯曲——摊平手时该指仍是屈的；若 $L_r^{\max} < \alpha L_h$，伸直也够不到，被限位钳住，表现为该指长期贴着限位、动态范围被压缩。任何相对指长比例与人不同的手指都会落进其中一种。

论文没有讨论这个问题，也没有提逐指缩放；它对形态差异的全部说明是「差异很大时（如 DClaw）需要手工指定关键点向量的对应关系」。我们的 little_scale 就是它 schema 里缺的那个旋钮。

补充一点公平的：它的 Huber 损失（作用在残差模长上）确实能限制「某根离谱的手指把整体带偏」的串扰，因为残差超过 $\delta$ 后梯度被截断为常数。但 Huber 不改变最优点的位置——只要弯曲能减小该行残差，最优解还是会弯。缓解串扰，不修正比例。

3.3 Shadow 的 10 向量配置：我们缺的那个结构性杠杆

这是本页从这篇论文里拿到的最有用的一条。dex-retargeting 里绝大多数手的配置都是「腕/掌 → 各指尖」，向量数等于手指数；Shadow Hand 是例外，它用 10 条：

手向量数组成
Allegro / LEAP4base → 4 指尖
Ability / Inspire / Schunk SVH5base → 5 指尖
Shadow10palm → 5 指尖 + palm → 5 个中节关节（thmiddle/ffmiddle/mfmiddle/rfmiddle/lfmiddle，人侧 landmark 2/6/10/14/18）
Panda 二指夹爪1leftfinger→rightfinger ↔ 人手拇指尖→食指尖

那 5 条 palm→中节 正是候选 a：给近端指节一个独立约束，让「总长度误差」分摊到两段，而不是全部由远端屈曲吸收——直击我们的根因 A。人侧索引也现成：MediaPipe 的 18 号点就是小指 PIP，与我们 FINGER_LANDMARKS["pinky"] = (17,18,19,20) 的第二个点是同一个关节（HTS 的 21 点布局与 MediaPipe 逐点对应）。

对我们而言这条几乎是免费的：往 l20_tasks 里加 VectorTask、在 MJCF 上补一个近节 site，求解器一行不用改。代价只有求解时间——Shadow 的 10 向量对 Allegro 的 4 向量，实测约 +80%（1.54 ms vs 0.84 ms，见下）。

3.4 DexPilot 捏合投影：机制与代价

治的不是小指，是精密抓取（手册问题表 #2）。做法：对人手的指尖间距做带迟滞的开关，一旦判定为「在捏」，就把参考向量换成「同方向、固定极小长度」，并把权重抬两个数量级。

开关（迟滞）
  1. 拇指↔各指：人手距离 < 0.03 m → 进入投影
  2. > 0.05 m → 退出；两者之间保持上一状态
  3. 非拇指两两：仅当其对应的两条拇指对都已投影且距离 ≤ 0.03 时才投影
投影后
  1. 参考向量长度：拇指对 $\eta_1=10^{-4}$ m，非拇指对 $\eta_2=3\times10^{-2}$ m
  2. 权重：1 → 200（拇指对）/ 400（非拇指对）
  3. 掌→指尖那几条权重恒定为「投影行数 + 指数」

物理含义：人手捏合时，视觉估计的指尖间距误差有几毫米，足以让机器人指尖差之毫厘抓空。投影把「人手 < 3 cm」直接翻译成「机器人指尖 0.1 mm 接触」，把感知误差从闭合环节里整个移除。论文的真机数据支持它：Two Cup Stacking 0.7 vs 0.3（对比 Robotic Telekinesis 的网络式 retargeting）。非拇指对的耦合条件也考究——食指–中指那一对只有在「拇指–食指」和「拇指–中指」都已进入捏合时才收拢，即只在多指同捏一个物体时才生效。

代价，以及为什么必须先上 bench。3–5 cm 是迟滞死区，必须张开到 5 cm 以上才解除；捏合区内人手的精细张合被完全抹掉——想「轻轻夹住但留 1 cm 缝」做不到。这和我们 2026-08-16 退役 clutch 手势时观察到的「一捏就粘住」是同一类交互副作用（当时 14/14 次触发都发生在抓握中途，平均冻结 14.7 s）。所以判据里必须带上操作者的主观报告，不能只看通过率。

3.5 整包引进的四个阻塞点

当初 dex.py 把 dex-retargeting 列为 Phase-2 的选项 1、最后选了选项 2（直接对着 MJCF 写自己的求解器），当时的三条理由现在逐条被证实，而且更严重：

阻塞点事实撞上我们的哪条约束
只吃 URDFvendored yourdfpy + pinocchio buildModelFromUrdf，没有 MJCF loader；且 model.nv != model.nq 直接 NotImplementedError我们只有 L20 的 MJCF，且它是仿真器实际在跑的那个模型
求解时间无上界NLopt LD_SLSQP，没有设置 maxeval / maxtime，只有 ftol_abs=1e-6I3：100 Hz 路径不许 stall。我们的固定 8 次迭代 + tol=0 正是为此
隐藏状态热启动 last_qpos 与 LPFilter 都挂在 self 上I5：同样的 landmark + 同样的 config 离线重跑必须逐位相同
手指零碰撞处理RobotWrapper.__init__ 里 if use_visual or use_collision: raise NotImplementedError。论文里的 “collision-free” 指的是 CuRobo 管的手臂与我们现状同级（我们也没有），不是退步但也不是收益

杂项，都可绕开但要知道：torch 是隐藏依赖（不在 dependencies 里，但 __init__.py 第一件事就是检查它）；Python 需 <3.13；机器人 URDF 在 git submodule 里，pip 包不含；每个手 × 左右 × 类型各需一个 yaml（仓库内 39 个）。

耗时的两组数字，供我们的预算对照：论文 Table II 报 retargeting 9±7 ms（desktop，各模块同机并跑），并说明检测模块上限 25 Hz、retargeting 跟着跑在 25 Hz。本页作者 2026-09-07 在 M4 Max 上按仓库自带的 example/profiling/profile_online_retargeting.py 实测（621 帧真实轨迹，OMP_NUM_THREADS=1）：Allegro vector 中位 0.65 ms / p99 2.10 / max 19.74；Shadow vector 中位 1.53 / p99 3.98；Shadow dexpilot 中位 1.96 / p99 4.71。500 Hz 在论文和仓库里都从未被演示过——这与「无迭代上限」是同一件事的两面。

3.6 两处论文与实现不一致

标注为不确定——现象可核对，作者意图未知。
（一）三个 optimizer 的 objective() 里，时间正则项 $\beta\|q_t-q_{t-1}\|^2$ 只被加进梯度、没有加进返回的目标函数值（result = huber_distance... 那一行不含它）。也就是说交给 SLSQP 的梯度不是所报告目标的梯度。实际效果更像是对搜索方向的阻尼，而非 line search 能看见的代价项。
（二）huber_delta / normal_delta 这两个 yaml 字段在 dexpilot 类型下根本不被读取（build() 的 dexpilot 分支不传它们），永远用构造函数默认值 0.03 / 4e-3。
另：Ability hand 被 tests/test_optimizer.py 的 DexPilot 测试显式排除，仓库未说明原因。

§ 4验证顺序与出口条件

建议顺序（每一步都是一天级的小实验，全部在 synthetic bench 上做完再上 rig）
  1. 先量，再修。跑一段只做小指开合的 session，看 q[pinky_mcp_roll] 时间序列与 n_at_limit：长时间钉在 ±0.23 则症状 2 的环节 1+2 确认；中段来回但幅度远小于 ±0.23 则环节 4 主导。这一步决定 c/d 要不要做，不做会在两个候选之间瞎猜。
  2. 候选 a（加 palm→PIP 向量）。判据见清单。同时记录求解时间 p95 的涨幅——它是这条的唯一硬代价。
  3. 候选 b（纵向分量缩放）。只有在 a 之后做才说得清功劳归属：a 若把 curl 修到 10° 以下，little_scale 就可以往回退，症状 2 自动缓解，b 可能根本不需要。
  4. 候选 e（DexPilot 投影）独立于上面三条，可并行，但必须带主观报告。
出口条件。任何一条候选跑出数据之后，结果（曲线、回归表、视频）搬进 Hand Control 技术路线手册，这一页在对应行留一句指过去的话。这一页永远只放还没有数据的东西——它是清单，不是记录。这也是它归在实验计划而不是实验记录的原因（STYLE §1 第 3–4 问）。
